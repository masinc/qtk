# To Tickets

計画・仕様・会話を、それぞれがブロックするチケットを宣言する**トレーサーバレット**の垂直スライスである**チケット**のセットに分解します。

イシュートラッカーとトリアージラベルの語彙は提供されているはずです — 提供されていない場合は `/setup-matt-pocock-skills` を実行してください。

## プロセス

### 1. コンテキストを集める

会話コンテキストにすでにあるものを使って作業します。ユーザーが引数として参照 (仕様のパス、イシュー番号、または URL) を渡した場合は、それを取得して完全なボディとコメントを読みます。

### 2. コードベースを探索する (任意)

まだ探索していなければ、コードベースを探索してコードの現在の状態を理解します。チケットのタイトルと説明はプロジェクトのドメイン用語集の語彙を使用し、触れる領域の ADR を尊重します。

実装を容易にするためにコードをプリファクタリングする機会を探します。「変更を簡単にしてから、簡単な変更を行う」。

### 3. 垂直スライスをドラフトする

作業を**トレーサーバレット**チケットに分解します。

<vertical-slice-rules>

- 各スライスは、すべてのレイヤー (スキーマ、API、UI、テスト) を通る狭いが完全なパスを切り抜く — 1 つのレイヤーの水平スライスではなく、垂直
- 完成したスライスは単独でデモ可能または検証可能
- 各スライスは単一の新しいコンテキストウィンドウに収まるサイズ
- プリファクタリングは最初に行うべき

</vertical-slice-rules>

各チケットに**ブロッキングエッジ**を与えます — 開始前に完了しなければならない他のチケット。ブロッカーがないチケットはすぐに開始できます。

**幅広のリファクタリングは垂直スライス化の例外です。** **幅広のリファクタリング**とは、1 つの機械的な変更 (カラムのリネーム、共有シンボルの型変更) であり、その**爆発半径**がコードベース全体に広がるため、1 つの編集で何千もの呼び出しサイトが同時に壊れ、どの垂直スライスもグリーンになれません。トレーサーバレットに無理に押し込まず、**expand–contract** として順序付けます。最初に expand: 古い形式の隣に新しい形式を追加して何も壊れないようにします。次に、呼び出しサイトを爆発半径に応じたバッチ (パッケージごと、ディレクトリごと) で移行し、各バッチは expand にブロックされた独自のチケットとし、古い形式がまだ存在するため CI はバッチごとにグリーンを維持します。最後に contract: 呼び出し元が残らなくなったら、すべての移行バッチにブロックされたチケットで古い形式を削除します。バッチが単独でもグリーンを維持できない場合は、順序は維持したまま、すべてが最終の integrate-and-verify チケットをブロックする共有統合ブランチを使わせます — グリーンはそこでだけ約束されます。

### 4. ユーザーにクイズする

提案された分解を番号付きリストとして提示します。各チケットについて表示します:

- **タイトル**: 短い説明的な名前
- **ブロック元**: 先に完了しなければならない他のチケット (あれば)
- **提供するもの**: このチケットが動くようにするエンドツーエンドの振る舞い

ユーザーに尋ねます:

- 粒度は適切か? (粗すぎる / 細かすぎる)
- ブロッキングエッジは正しいか — 各チケットは本当に自分をゲートするチケットだけに依存しているか?
- チケットをマージしたり、さらに分割すべきものはあるか?

ユーザーが分解を承認するまで反復します。

### 5. 設定されたトラッカーにチケットを公開する

承認されたチケットを公開します。**方法**は `/setup-matt-pocock-skills` が設定したトラッカーに依存します — チケット自体はどちらの場合も同じで、ブロッキングエッジの形だけが変わります:

- **qtk CLI** → `bunx @masinc/qtk issue create` でチケットを作成します。依存順 (ブロッカーが先) で作成し、`--dep` オプションでブロッキングエッジを設定します。各チケットの ID は共通採番で自動採番されます。`--tag` で `ready-for-agent` を付与します。以下の qtk CLI ワークフローを使用します。
- **ローカルファイル** → `.scratch/<feature-slug>/issues/<NN>-<slug>.md` の下にチケットごとに 1 ファイルを書き、依存順 (ブロッカーが先) で `01` から番号を付けます。各ファイルの "Blocked by" は依存する番号・タイトルをリストします (後方互換性のため維持)。以下のチケットごとのファイルテンプレートを使用します — 1 チケット 1 ファイルで、単一の結合ファイルは決して作らないでください。
- **本物のイシュートラッカー (GitHub、Linear など)** → 各チケットのブロッキングエッジが実際の識別子を参照できるよう、依存順 (ブロッカーが先) でチケットごとに 1 イシューを公開します。プラットフォームが持つネイティブのブロッキング・サブイシュー関係を使用し、なければ各チケットの "Blocked by" にブロックするイシューを設定します。特に指示がない限り `ready-for-agent` トリアージラベルを適用します — チケットは構造上エージェントが取得可能です。

**フロンティア**を消化します: すべてのブロッカーが完了しているチケット。qtk CLI の場合は `bunx @masinc/qtk issue list --ready` で取得します。純粋な線形チェーンでは上から下へとなります。

親イシューをクローズしたり変更したりしないでください。

<qtk-ticket-workflow>

各チケットを作成します (ブロッカーが先、依存順で作成):

```bash
bunx @masinc/qtk issue create "チケットタイトル" -d "ユーザーの視点から見た、このチケットが動くようにするエンドツーエンドの振る舞い" --ac "受け入れ基準1" --ac "受け入れ基準2" --tag ready-for-agent --dep 0001
```

- `--dep` には先行チケットの ID を指定します (複数指定可)。ブロッカーがない場合は省略します
- `--ac` で受け入れ基準を複数指定します
- `--tag ready-for-agent` でトリアージラベルを付与します
- ID は共通採番で自動採番されます (例: `#0001`)

フロンティア (実行可能なチケット) を確認します:

```bash
bunx @masinc/qtk issue list --ready
```

</qtk-ticket-workflow>
