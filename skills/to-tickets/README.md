## 何をするスキルか

`to-tickets` は、計画、[仕様](https://www.aihero.dev/ai-coding-dictionary/spec)、またはあなたがいる会話を、イシュートラッカー上の一連の**[チケット](https://www.aihero.dev/ai-coding-dictionary/ticket)** に分解します。各チケットは**ブロッキングエッジ**を宣言します — それを始める前に終わらなければならない他のチケット。

すべてのチケットは**トレーサーバレット**です: 変更のすべての層 — スキーマ、API、UI、テスト — を通る狭いが完全なパスで、着地した瞬間に単独でデモできます。それが、作業を分割する明白な方法 — 一度に1つの層を切り、最後に統合する — と異なる振る舞いをさせる制約です。また、各チケットを単一の新しい[コンテキストウィンドウ](https://www.aihero.dev/ai-coding-dictionary/context-window)に収まるサイズにします。チケットを拾うのは、あなたの仕様を見たことのない[セッション](https://www.aihero.dev/ai-coding-dictionary/session)だからです。

## いつ使うか

`/to-tickets` と入力して起動します — [エージェント](https://www.aihero.dev/ai-coding-dictionary/agent)は自分からは使いません。

| あなたがいるところ | 実行するもの |
| --- | --- |
| 仕様イシューがあり、ビルドがいくつかのセッションにまたがる | `/to-tickets`、または `/to-tickets #<spec_issue>` |
| 計画が会話にのみあり、書き起こされていない | `/to-tickets` はスレッドを直接読む — 仕様は不要 |
| 変更全体が1つのコンテキストウィンドウに収まる | [implement](https://aihero.dev/skills-implement) — チケットをスキップ |
| まだ何も決めていない | [grill-with-docs](https://aihero.dev/skills-grill-with-docs)、それから [to-spec](https://aihero.dev/skills-to-spec) |
| [wayfinder](https://aihero.dev/skills-wayfinder) の地図がクリアされた | 地図を崩壊させるためにまず [to-spec](https://aihero.dev/skills-to-spec)、それから `/to-tickets` |

`to-tickets` が生成したチケットは構成的にエージェント対応です。それらに [triage](https://aihero.dev/skills-triage) を実行しないでください — triage は他人から届いた作業のためのものです。

## 前提条件

`to-tickets` はトラッカーに公開するので、[setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) がこのリポジトリにトラッカーとトリアージラベル語彙を設定している必要があります。どちらの種類でも機能します: GitHub や Linear のような実際のトラッカー、または箱から出してサポートされる `.scratch/` の下のローカル markdown ファイル。

## レイヤーではなくトレーサーバレット

**水平**スライスは変更の1つの層を出荷します。すべての層が着地するまで何も機能せず、各チケットの受け入れ基準は別のチケットが所有する作業に手を伸ばさなければなりません。**垂直**スライス — トレーサーバレット — はすべての層を通る1つの薄いパスを同時に出荷するので、単独で検証可能で、成績をつけるすべてを所有します。

これは人々が最も頻繁に破るルールであり、結果はよく文書化されています。あるチームは層別に切った26チケットのスタック — corpus、producer、aggregator、selector — を実行し、クローズしたチケットごとに約20回のエージェント実行を得て、その約4分の3がやり直しでした。彼ら自身のポストモーテムは、すべての失敗クラスを実装ではなく水平スライスにたどりました。

何かが公開される前に2つのことが起こります。`to-tickets` はプレファクタリングを探します — 「変更を簡単にし、それから簡単な変更をする」 — そしてその作業を最初に順序付けます。それから分解を番号付きリストとして提示し、あなたにクイズします: 粒度は正しいか、ブロッキングエッジは本物か、何かをマージまたは分割すべきか。あなたが承認するまで何もトラッカーに到達せず、そのクイズが押し返す場所です。

## ブロッキングエッジ

エッジがアーティファクトの要点です。トラッカーによって2つの方法で読まれます:

| トラッカー | エッジの場所 | 作業の仕方 |
| --- | --- | --- |
| ローカル markdown | `.scratch/<feature>/issues/<NN>-<slug>.md` のチケットごとに1ファイルのテキスト。ブロッカーが最初に番号付け | 上から下へ、手で |
| 実際のトラッカー(GitHub、Linear) | ネイティブのブロッキングリンク、またはトラッカーが持っていればサブイシュー | ブロッカーが終わったチケットは**フロンティア**にあり、掴める |

どちらにせよエッジはチケットの中に生きます。媒体は、何かがそれらに並列に行動できるかどうかだけを決めます。`to-tickets` はアーティファクトを生成します。それを実行する — 一度に1セッション、または一団で — のはスキルではなくあなたの仕事です。

## 広範リファクタリングの例外

1つの形がトレーサーバレットのルールを破ります。**広範リファクタリング**は単一の機械的な変更 — 列のリネーム、共有シンボルの型変更 — であり、その**爆発半径**がコードベース全体に広がるので、1つの編集が何千もの呼び出しサイトを壊し、垂直スライスが緑に着地できません。

`to-tickets` はそれを代わりに**expand–contract(拡張–収縮)** として順序付けます:

- **Expand** — 古いものの隣に新しい形を追加し、何も壊れないようにする。
- **Migrate** — 爆発半径でサイズ調整したバッチ(パッケージごと、ディレクトリごと)で呼び出しサイトを移動。バッチごとに1チケット、それぞれが expand によってブロックされる。古い形がまだ存在するので CI は緑のまま。
- **Contract** — 呼び出し側が残っていなくなったら古い形を削除。すべての migrate バッチによってブロックされるチケットで。

バッチさえ単独で緑を保てない場合、それらは統合ブランチを共有し、すべてが最終的な統合・検証チケットをブロックします。緑はそこでだけ約束されます。

## よくある質問

**3行の変更に12のチケットを生成した。**

過剰分解はこのスキルで最も報告される摩擦であり、実践者間で一貫しています: [モデル](https://www.aihero.dev/ai-coding-dictionary/model)は原子的な単位にデフォルトし、それらを意味のあるものにするグルーピングを失います。クイズステップはまさにこのために存在します — マージするよう頼めば、マージします。より深い答えは、チケットには床があるということです: 変更全体が1つのコンテキストウィンドウに収まるなら、このスキルはまったく必要ありません。[implement](https://aihero.dev/skills-implement) に直接行ってください。

**チケットがレイヤーごとに1つ出てきた — すべてのスキーマが1つに、すべての API が別に。**

これは垂直スライスルールが書かれた相手の失敗であり、スキルは時々まだそれを生み出します。クイズステップで、チケットごとに1つの質問をすることで捕捉してください: これが終わったときに何をデモできる? 答えのないチケットは水平スライスです。この理由で各チケットに「demo path」行を追加する人もおり、モデルを垂直分解へ促すと報告しています。

**GitHub でチケットが仕様イシューのサブイシューとして作成されなかった。**

既知で未修正。十数回の実行といくつかのモデルにまたがって報告され、[issue #554 で最も完全に](https://github.com/mattpocock/skills/issues/554)報告され、Codex では Claude より悪いです。`gh` は v2.94 以降これをネイティブにサポートしています: `gh issue create --parent <n>`、および後で `gh issue edit <parent> --add-sub-issue <n>`。トラッカーテンプレートがそれらを優先するまで、実行後に親リンクを自分で配線するのが信頼できる動きです。

**「Blocked by」が本当のブロッキングリンクではなくイシュー本文に書かれた。**

同じクラスの問題で、[issue #513](https://github.com/mattpocock/skills/issues/513) で報告され、エージェントは GitHub にはネイティブのブロッキング関係がまったくないと主張するところまで行きました。あります — `gh issue create --blocked-by 12,15`。ブロッカーが最初に公開されるので、その番号は作成時に常に利用可能です。本文テキストはネイティブエッジのないトラッカーのフォールバックであることを意図されており、デフォルトではありません。

**ローカルチケットはどこへ行く? v1.1 ノートはルートレベルの `tickets.md` と言っていた。**

そう言いました、そしてそれはバグでした — 単一の共有ファイルは、並列エージェントがそれに書いたときにも競合しました。ローカルモードは今や、依存順で、ローカルトラッカーテンプレートがすでに説明したレイアウトに一致して、`.scratch/<feature-slug>/issues/<NN>-<slug>.md` の下にチケットごとに1ファイルを書きます。`NN` プレフィックスは本当のチケット ID なので、長いタイトルを打ち直す代わりに `/implement 03` が機能します。

**仕様を読もうとしたときに切り詰め続けた。**

非常に大きな仕様は、トラッカーイシューがきれいに提供し返すものを超えて育つことがあり、フォールバックするローカルコピーはありません — エージェントはチャンクを再取得するのに[ツール呼び出し](https://www.aihero.dev/ai-coding-dictionary/tool-call)を燃やし、決して終わりに到達しません。`/to-spec` と `/to-tickets` の間で[クリア](https://www.aihero.dev/ai-coding-dictionary/clearing) や[コンパクト](https://www.aihero.dev/ai-coding-dictionary/compaction) をしないでください。同じコンテキストウィンドウで実行すれば、仕様はまったく取得し直される必要がありません。

**受け入れ基準が何も成績をつけなかった — 作業が行われる前にいくつかパスした。**

テンプレートは基準を求め、それらが失敗できるかについて何も言わないので、これは起こります。3つの形が繰り返します: ベースコミットで既に真の基準、別のチケットが所有する作業によってのみ満たせる基準、そしてアーティファクトから導出するのではなくリクエストを言い直す基準。垂直スライスはそのほとんどを防ぎます — 以前に存在しなかった振る舞いを届けるスライスは構成的にベースコミットで赤です — しかし、チェックは手で行う価値があります。各基準について、それが偽であることを示す観察を名指しし、実装者が開始するコミットで失敗することを確認してください。

**チケットが公開された。実際にどう実行する?**

スキルはアーティファクトで止まり、自動ディスパッチモードはありません。ディスパッチは手動です: ボードを見て、オープンブロッカーのないチケットを数え、その数のエージェントセッションを開きます。新しいコンテキストごとに1チケット、その間でクリア。[implement](https://aihero.dev/skills-implement) は GitHub でもローカル markdown でも、終わったときにチケットを確実に閉じたりチェックしたりしないことを認識しておいてください。チケットの状態はあなたが更新するものです。

## うまく機能しているなら

- すべてのチケットが「これが終わったときに何をデモできる?」への答えを持ち、答えがレイヤーではなく振る舞いである。
- リストが番号付きで返ってきて、それぞれに「Blocked by」行がある。何かが公開される前に。
- 先頭のチケットにブロッカーがなく、すぐに開始できる。
- チケット本文の何もがファイルパスや行番号ではない。プロトタイプが生成したスニペットを除いて。
- 各チケットが、あなたが部屋にいなくても新しいセッションが終わらせられるもののように読める。
- 見つけたプレファクタリングがフィーチャーチケットに混ざるのではなく順序の先頭にある。

## どこに位置づくか

`to-tickets` はメインビルドチェーンのステップです:

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

上流は [to-spec](https://aihero.dev/skills-to-spec) で、スライスする確定した仕様を渡します — 両方を1つの途切れないコンテキストウィンドウに保ってください。下流は [implement](https://aihero.dev/skills-implement) で、新しいセッションごとに1チケットを構築し、テストのために [tdd](https://aihero.dev/skills-tdd) を駆動し、[code-review](https://aihero.dev/skills-code-review) で締めくくります。どのスキルやフローが合うか分からないときは、[ask-matt](https://aihero.dev/skills-ask-matt) がルーティングします。
