# ドメイン文書

エンジニアリングスキル群が、コードベースを探索するときにこのリポジトリのドメイン文書をどのように利用すべきか。

## 探索する前に、これらを読む

- リポジトリルートの **`CONTEXT.md`**、または
- 存在すればリポジトリルートの **`CONTEXT-MAP.md`** — 各コンテキストに 1 つの `CONTEXT.md` を指しています。トピックに関連する各コンテキストを読みます。
- **`docs/adr/`** — これから作業する領域に触れる ADR を読みます。マルチコンテキストリポジトリでは、コンテキストスコープの決定について `src/<context>/docs/adr/` も確認します。

これらのファイルのいずれかが存在しない場合は、**黙って進めます**。欠落を指摘せず、先に作成することを提案しないでください。`/domain-modeling` スキル (`/grill-with-docs` と `/improve-codebase-architecture` 経由で到達) は、用語や決定が実際に解決されるときに遅延的にそれらを作成します。

## ファイル構成

シングルコンテキストリポジトリ (ほとんどのリポジトリ):

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

マルチコンテキストリポジトリ (ルートに `CONTEXT-MAP.md` がある場合):

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← システム全体の決定
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← コンテキスト固有の決定
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 用語集の語彙を使う

出力でドメイン概念に名前を付けるときは (イシュータイトル、リファクタリング提案、仮説、テスト名など)、`CONTEXT.md` で定義されている用語を使います。用語集が明示的に避けている同義語に流れないでください。

必要な概念がまだ用語集にない場合は、それがシグナルです — プロジェクトが使っていない言葉を発明しているか (再考する)、または本当のギャップがあるか (それを `/domain-modeling` 用にメモする) です。

## ADR のコンフリクトをフラグする

出力が既存の ADR と矛盾する場合は、黙って上書きするのではなく、明示的に表面化します:

> _ADR-0007 (event-sourced orders) と矛盾する — ただし再検討する価値があるのはなぜなら…_
