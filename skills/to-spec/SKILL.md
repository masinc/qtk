このスキルは、現在の会話コンテキストとコードベースの理解を取り込んで仕様を生成します。ユーザーにインタビューをしないでください — すでに知っていることを総合するだけです。

イシュートラッカーとトリアージラベルの語彙は提供されているはずです — 提供されていない場合は `/setup-matt-pocock-skills` を実行してください。

## プロセス

1. まだ探索していなければ、リポジトリを探索してコードベースの現在の状態を理解します。仕様全体でプロジェクトのドメイン用語集の語彙を使用し、触れる領域の ADR を尊重します。

2. 機能をテストするシームをスケッチします。既存のシームは新しいシームより優先されます。可能な限り高いシームを使用します。新しいシームが必要な場合は、可能な限り高い位置に提案します。コードベース全体のシームは少なければ少ないほど良い — 理想は 1 つです。

それらのシームがユーザーの期待に合っているか確認します。

3. 以下のテンプレートを使って仕様を書き、プロジェクトのイシュートラッカーに公開します。`ready-for-agent` トリアージラベルを適用します — 追加のトリアージは不要です。

**qtk CLI の場合**:

```bash
bunx @masinc/qtk spec create "仕様タイトル" -d "仕様の要約"
bunx @masinc/qtk spec update <ID> --content "仕様本文 (spec-template に沿った Markdown)"
```

または、`spec create` で作成したファイルを直接編集して本文を書き込むこともできます (`.qtk/specs/<NNNN>-<slug>.md`)。仕様を issue としてトラッカーに公開する場合は `bunx @masinc/qtk issue create "仕様タイトル" --tag ready-for-agent` を使用します。

**ローカルファイルの場合**: `.scratch/<feature-slug>/spec.md` に以下のテンプレートで書き込みます。

**本物のイシュートラッカー (GitHub、Linear など) の場合**: イシュートラッカーに仕様を公開し、`ready-for-agent` ラベルを適用します。

<spec-template>

## Problem Statement (問題の記述)

ユーザーの視点から見た、ユーザーが直面している問題。

## Solution (解決策)

ユーザーの視点から見た、問題の解決策。

## User Stories (ユーザーストーリー)

長い、番号付きのユーザーストーリーのリスト。各ユーザーストーリーは次の形式で記述します:

1. <actor>として、私は<feature>が欲しい。それにより<benefit>が得られるからだ。

<user-story-example>
1. モバイルバンキングの顧客として、私は口座の残高を確認したい。それにより支出についてより情報に基づいた意思決定ができるからだ。
</user-story-example>

このユーザーストーリーのリストは非常に網羅的で、機能のすべての側面をカバーすべきです。

## Implementation Decisions (実装の決定)

行われた実装上の決定のリスト。次のものを含めることができます:

- 構築・変更されるモジュール
- 変更されるそれらのモジュールのインターフェース
- 開発者からの技術的な明確化
- アーキテクチャ上の決定
- スキーマの変更
- API コントラクト
- 具体的な相互作用

特定のファイルパスやコードスニペットは含めないでください。すぐに古くなる可能性があります。

例外: プロトタイプが、散文よりも正確に決定をコード化したスニペット (状態機械、リデューサー、スキーマ、型の形) を生み出した場合は、関連する決定内にインラインで埋め込み、プロトタイプ由来であることを簡単に注記します。決定の本質を含む部分だけに切り詰めます — 動くデモではなく、重要な部分だけです。

## Testing Decisions (テストの決定)

行われたテスト上の決定のリスト。次のものを含めます:

- 良いテストを構成するものの説明 (実装の詳細ではなく外部の振る舞いのみをテストする)
- テストされるモジュール
- テストの先行例 (コードベース内の類似タイプのテスト)

## Out of Scope (対象外)

この仕様の対象外となるものの説明。

## Further Notes (その他のメモ)

機能に関するその他のメモ。

</spec-template>
