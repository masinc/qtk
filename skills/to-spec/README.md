## 何をするスキルか

`to-spec` は、ちょうど終えた会話を**[仕様](https://www.aihero.dev/ai-coding-dictionary/spec)** に変え、単一のイシューとしてイシュートラッカーに公開します。

あなたにインタビューしません。これに手を伸ばす頃には決定はすでに終わっているので、知られているもの — スレッドから、コードベースから、あなたの `CONTEXT.md` と ADR から — を統合し、新しい質問のラウンドを開きません。仕様はすでに行われた決定の記録であり、新しいものが行われる場所ではありません。

## いつ使うか

`/to-spec` と入力して起動します — [エージェント](https://www.aihero.dev/ai-coding-dictionary/agent)は自分からは使いません。

ビルドが1つのエージェント[セッション](https://www.aihero.dev/ai-coding-dictionary/session)に大きすぎて、いくつかに分割して生き残らなければならないときに使います。それがトリガーのすべてです:

| あなたがいるところ | 実行するもの |
| --- | --- |
| まだ何も決めていない | まず [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 決めた、作業が1つの[コンテキストウィンドウ](https://www.aihero.dev/ai-coding-dictionary/context-window)に収まる | [implement](https://aihero.dev/skills-implement) — 仕様をスキップ |
| 決めた、作業がいくつかのセッションにまたがる | `/to-spec`、それから [to-tickets](https://aihero.dev/skills-to-tickets) |
| [wayfinder](https://aihero.dev/skills-wayfinder) の地図がクリアされた | `/to-spec #<map_issue>` |

## 前提条件

`to-spec` は仕様をイシューとして公開するので、[setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) がこのリポジトリのトラッカーとトリアージラベル語彙を設定している必要があります。どちらの種類でも機能します: GitHub のような実際のトラッカー、または箱から出してサポートされる `.scratch/` の下のローカル markdown ファイル。

## 仕様は決定記録

仕様が存在するのは、コンテキストウィンドウが終わるからです。[grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) の間に確定させたすべて — 解決策の形、議論し抜いた選択、意図的に拒否したもの — が、まさにクリアされようとしている1つの会話にあります。仕様はそれを生き残るものです。

したがって、何も検証せず、何も決定しません。プロジェクト自身の語彙で決定されたものを捕捉し、新しいセッションがあなたに再説明を求めずに作業を拾えるようにします。仕様が主張するものであなたが実際に言ったことがないものは、欠陥です。

## 散文より先にシーム

一言も書く前に、`to-spec` はフィーチャーがテストされる**シーム**をスケッチし、あなたと確認します。新しいシームより既存のシームを好み、取れる最高のシームを取ります — 変更全体の理想的な数は1つです。

合意されたシームはその後旅をします。[tdd](https://aihero.dev/skills-tdd) は事前に合意されたシームでのみ機能し、[code-review](https://aihero.dev/skills-code-review) は差分を仕様と照らしてレビューするので、誰も合意しなかったシームはレビュー指摘として現れます。束縛は間接的です — それはこの文書を通じて実行されます — それがまさに、シームの会話を実装に先送りするのではなくここで真剣に取る価値がある理由です。

## よくある質問

**`/to-prd` はどこへ行った?**

それがこのスキルで、v1.1 でリネームされました。「Spec」は今や単一のスレッドを貫く用語で、古い `to-prd` スラグは死んでいます — 新しい名前で再インストールしてください。古い語彙を置き換えたペアは*spec* と*tickets* です: 仕様は目的地とそれを固定する決定、[チケット](https://www.aihero.dev/ai-coding-dictionary/ticket)はそこに到達する実行ステップ。ピボットするなら、未完成のチケットを削除して仕様を保持してください。

**なぜ仕様が `ready-for-agent` ラベルを得る? エージェントに実装されたくない。**

そのラベルは「さらなるトリアージ不要」を意味します — 文書はエージェントが作業するのに十分完全です。それは入力指定であり、作業命令ではありません。しかし、`ready-for-agent` をポーリングする [AFK](https://www.aihero.dev/ai-coding-dictionary/afk) エージェントを実行すると、その区別は彼らに見えず、チケットスライスを拾う代わりに1回の実行で仕様全体を構築しようと喜んで試みます。これはスキルで最も報告される粗いエッジです。変わるまで、AFK エージェントのプロンプトで親の仕様を明示的に除外するか、`/to-tickets` が実行されたらラベルを剥がしてください。

**grilling から `/to-tickets` に直接行って仕様をスキップしては?**

しばしばそうすべきです — 仕様はマルチセッション作業でのみステップを稼ぎます。それが報うのは、チケットが使い捨てで仕様がそうでないことです: 各チケットは1つの新しいコンテキストウィンドウにサイズ調整され、削除またはクローズされる一方、仕様はその背後の推論が住む唯一の場所として残ります。単一セッションの変更ではそれは何も買わず、[モデル](https://www.aihero.dev/ai-coding-dictionary/model)が漂流できる余分な統合ステップを払っています。grilling → `/implement` に行ってください。

**wayfinder の地図を終えたばかり。何を供給する?**

メインのマップイシュー — `/to-spec #<map_issue>`、個々の決定チケットではありません。[wayfinder](https://aihero.dev/skills-wayfinder) はデリバラブルではなく決定を、地図中に散らばって生み出します。`to-spec` はそれらを1つの構築可能な文書に崩壊させるステップです。地図を `/implement` に直接ループすると、その崩壊を捨てます。

**仕様は私がレビューするため? それともエージェントのためだけ?**

ほとんどエージェントのためで、そのように読めます — 完全で、密度が高く、参照が重い。あなたの目に価値がある部分はシームとアウトオブスコープセクションです。間違った決定を最も安く捕捉し、後で発見するのに最も高価な2か所だからです。全体を最初から最後まで読むことは人々が持つ本当の不満であり、サマリーモードはありません。正直な答えは、仕様があなたを驚かせるなら、grilling が浅すぎたのであって、仕様が長すぎたのではないということです。

**チケットが始まったら仕様を凍結するか、エージェントに書き直させる?**

それを同期に保つものは何もないので、実際にはそれはその瞬間に知っていたことのスナップショットであり、実装が何かを教えてくれる最初の回で古くなります。作業が出荷されたら使い捨てとして扱ってください。それを長生きさせることを意図されたアーティファクトはあなたの `CONTEXT.md` と ADR です — 実装中に学んだ何かが長持ちする価値があるなら、それは編集された仕様ではなくそこに属します。

**私の作業はリファクタリングやモジュール境界であり、フィーチャーではない。テンプレートは合いますか?**

あまり合わず、これは既知の制限です。テンプレートはユーザーストーリーに強く寄っており、それはアーキテクチャ作業には間違った形です — 実際にはインターフェースと不変条件に関する決定の周りに、誰も頼んでいないストーリーを書くことになります。代わりに実装決定とテスト決定セクションに寄りかかり、耐久性のあるアーキテクチャの呼び出しを仕様に担わせようとするのではなく [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 経由で ADR として着地させてください。

**関連作業をトラッカーでチェックしたり、尊重する ADR を引用したりしますか?**

両方ともノー。触れる領域をカバーする ADR を読み、尊重しますが、リンクはせず、ドラフト前に重複するイシューをトラッカーで検索しません — そのため、仕様が誰かがすでに提出した作業を静かに複製することがあります。領域が混雑しているなら、先に自分でトラッカーを検索してください。

**`/to-tickets` が私の仕様を読めなかった — 切り詰め続けた。**

非常に大きな仕様は、トラッカーイシューがきれいに提供し返すものを超えて育つことがあり、フォールバックするローカルコピーはありません。修正はコンテキスト衛生です: `/to-spec` と `/to-tickets` の間で[クリア](https://www.aihero.dev/ai-coding-dictionary/clearing) や[コンパクト](https://www.aihero.dev/ai-coding-dictionary/compaction) をしないでください。同じウィンドウで実行すれば、仕様はまったく再取得される必要がありません。

## うまく機能しているなら

- 新しい質問のラウンドを尋ねる代わりに書き始める。
- 書く前にシームをあなたに提示し、逃げられる限り少なく提案する。
- プロジェクトの名詞で返ってくる。一般的なプロダクトマネジメントのボイラープレートではない。
- その中のすべての決定が、行ったことを覚えているもの。セクションを埋めるために発明されたものは何もない。
- アウトオブスコープセクションに本物のものが入っている — 拒否したものが通常ページで最も有用な行です。

## どこに位置づくか

`to-spec` はメインビルドチェーンのステップであり、そのマルチセッションブランチでのみ:

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

上流の隣人は、このスキルが記録するだけの決定を行う [grill-with-docs](https://aihero.dev/skills-grill-with-docs) と、完成した地図がまさにここでチェーンに合流する [wayfinder](https://aihero.dev/skills-wayfinder) です。下流では、[to-tickets](https://aihero.dev/skills-to-tickets) が仕様を [implement](https://aihero.dev/skills-implement) が構築するトレーサーバレットチケットに切ります。どのスキルやフローが合うか分からないときは、[ask-matt](https://aihero.dev/skills-ask-matt) がルーティングします。
