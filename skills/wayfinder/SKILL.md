大まかなアイデアが届きました — 1 つのエージェントセッションには大きすぎ、霧に包まれています: ここから**目的地**への道はまだ見えていません。Wayfinding とは、目的地に向かって突進することではなく、その道を見つけることです。このスキルは、リポジトリのイシュートラッカー上で**共有マップ**として道筋を描き、その**決定チケット** — 実行するビルドのスライスではなく、解決が決定となる質問 — をルートが明確になるまで 1 つずつ消化します。

目的地は取り組みごとに異なり、その命名が地図作成の最初の行為です — すべてのチケットを形作ります。それは引き渡して反復する仕様かもしれませんし、計画を始める前に確定する決定かもしれませんし、データ構造のマイグレーションのようにその場で行う変更かもしれません。マップはドメインに依存しません — エンジニアリング作業、コースコンテンツ、形に合うものであれば何でも。

## 実行するのではなく計画する

Wayfinder はデフォルトで**計画**です: 各チケットは決定を解決し、マップは道が見えたときに完成です — 誰かが実際にやる前に決定すべきことが何も残っていない状態。ただ作業をしてしまいたいという引力は通常、マップの端に到達して引き渡し時だというシグナルです。取り組みはその **Notes** でこれを上書きできます — 実行をマップ自体に持ち込む — しかしそれがなければ、成果物ではなく決定を生み出します。

## 名前で参照する

すべてのマップとチケットはイシューなので、**名前** — そのタイトル — を持ちます。人間が読むすべてのもの (ナレーション、マップの Decisions-so-far) で、その名前で参照し、裸の ID、番号、スラッグでは決して参照しないでください。`#42, #43, #44` の壁は読みにくく、名前は一目で読めます。ID と URL は消えません — 名前がリンクを包み込みます — ただしそれらは名前の_内側_に乗り、その代わりには決してなりません。

## マップ

マップはこのリポジトリのイシュートラッカー上の 1 つのイシューで、`wayfinder:map` というラベルが付いています — 正規のアーティファクトです。そのチケットはマップの子イシューです。qtk CLI の場合は、マップは `qtk plan create` で作成される plan 種別のドキュメントで、`wayfinder:map` タグを付与します (`bunx qtk plan create "計画名" --status in-progress`)。

マップは**索引**であり、ストアではありません。下された決定をリストし、その詳細を保持するチケットを指し示します。決定は正確に 1 か所 — そのチケット — に存在するため、マップはそれを繰り返さず、要約してリンクするだけです。

**マップ、その子チケット、ブロッキング、フロンティアクエリが物理的にどこに存在するかはトラッカー固有です。** イシュートラッカーは提供されているはずです — 提供されていない場合は `/setup-matt-pocock-skills` を実行してください。トラッカードキュメントの "Wayfinding operations" セクションで、_この_リポジトリがそれらをどう表現するかを確認します。トラッカーが提供されていない場合は、qtk CLI をデフォルトにします。

**qtk CLI の場合**: マップは `qtk plan create` で作成される plan 種別、子チケットは `qtk issue create` で作成される issue 種別、ブロッキングは `--dep` オプション (frontmatter の `dependencies` 配列)、フロンティアは `qtk issue list --ready`、クレームは `qtk issue claim` で管理します (milestone は使用しません)。

### マップのボディ

セッションごとに 1 回ロードされる、低解像度のマップ全体です。オープンなチケットは**リストされません** — それらはクエリで見つかるオープンな子イシューです。

```markdown
## Destination

<このマップの終わりに到達したときに見えるもの — この取り組みが進む仕様、決定、または変更。1〜2 行。すべてのセッションはチケットを選ぶ前にこれに向き合います。>

## Notes

<ドメイン。すべてのセッションが参照すべきスキル。この取り組みのための常設の好み>

## Decisions so far

<!-- 索引 — クローズしたチケットごとに 1 行: 関連性を判断するのに十分な内容、詳細はチケットが保持するリンクを拡大して見る -->

- [<クローズしたチケットのタイトル>](link) — <回答の 1 行の要約>

## Not yet specified

<!-- "Fog of war" を参照: まだチケット化できない対象内の霧。フロンティアが進むにつれて卒業する -->

## Out of scope

<!-- "Out of scope" を参照: 目的地を超えると判断された作業。クローズされ、決して卒業しない -->
```

### チケット

各チケットはマップの**子イシュー**です。トラッカーのイシュー ID がその ID です。qtk CLI の場合は `qtk issue create` で作成し、`--dep <マップの issue ID>` でマップに紐付けます。ボディは質問で、1 回の 100K トークンのエージェントセッションに収まるサイズです:

```markdown
## Question

<このチケットが解決する決定または調査>
```

各チケットは `wayfinder:<type>` ラベルを持ちます — `research`、`prototype`、`grilling`、`task` のいずれかです ([チケットタイプ](#チケットタイプ) を参照)。qtk CLI の場合は `--tag wayfinder:<type>` でタグを付与します (例: `bunx qtk issue edit <ID> --add-tag wayfinder:research`)。

セッションは、作業の**前に**、マップをドライブする開発者に割り当てることでチケットを**クレーム**し、並行セッションがそれをスキップするようにします。そのアサイニーこそがクレームです: オープンで未アサインのチケットは未クレームです。qtk CLI の場合は `bunx qtk issue claim <ID> --as "<名前>"` で原子的にクレームします。

ブロッキングはトラッカーの**ネイティブ**な依存関係を使用します — フロンティアがトラッカー自身の UI に_視覚的に_レンダリングされ、人間がマップを開かなくても何が取れるか見えるため、これは不可欠です。ネイティブのブロッキングを持たないトラッカーだけがボディ規約にフォールバックします。qtk CLI の場合は `--dep` オプション (frontmatter の `dependencies` 配列) で構造化依存を管理します。チケットは、それをブロックするすべてのチケットがクローズされたときに**アンブロック**され、**フロンティア**はオープンでアンブロックされ未クレームの子 — 既知の端です。qtk CLI の場合は `bunx qtk issue list --ready` でフロンティアを取得します。

回答はボディの一部ではありません — 解決時に記録されます ([マップを消化する](#マップを消化する) を参照)。チケット解決中に作成されたアセットは、貼り付けではなくイシューからリンクされます。

## チケットタイプ

すべてのチケットは **HITL** — 人間がループにいて、自ら発言する人間と_一緒に_作業する — または **AFK** — エージェントだけでドライブされる — のいずれかです。HITL チケットはそのライブなやりとりを通じてのみ解決します。エージェントはその人間側の代役には決してなりません (自分の質問に自分で答えるグリリングエージェントはこれを破っています)。

- **Research** (AFK): ドキュメント、サードパーティ API、ナレッジベースなどのローカルリソースを読んで、決定が待つ事実を表面化します。`/research` **サブエージェント**によって解決されます。現在の作業ディレクトリの外の知識が必要なときに使用します。
- **Prototype** (HITL): 反応するための安価で粗く具体的なアーティファクト — アウトライン、ラフな試案、スタブ、または /prototype スキルによる UI・ロジックコード — を作って議論の解像度を高めます。プロトタイプをアセットとしてリンクします。「どう見えるべきか」「どう振る舞うべきか」が鍵となる質問のときに使用します。
- **Grilling** (HITL): 会話。デフォルトのケースです。常に /grilling と /domain-modeling スキルを呼び出します。
- **Task** (HITL または AFK): _決定_が下される前に発生しなければならない手動作業 — 決定することも、プロトタイプすることも、リサーチすることもないが、それが完了するまで議論がブロックされる。サービスの API を判断できるようにサインアップする、アクセスをプロビジョニングする、形が見えるようにデータを移動する。これは決定ではなく_実行_をする唯一のタイプです — そして目的地を届けるのではなく決定をアンブロックすることでその地位を得ます。エージェントはできるところでは単独でドライブし (AFK)、そうでなければ人間に正確なチェックリストを渡します (HITL)。作業が完了したときに解決し、回答は何を行ったかと、後のチケットが依存する結果の事実 (認証情報の場所、新しい URL、行数) を記録します。

## 霧の戦争 (Fog of war)

マップは_意図的に_不完全です: まだ見えないものを描いてはいけません。ライブチケットの向こうには**霧の戦争**があります — 来ることが分かるが、まだ開いている質問に依存しているため特定できない決定や調査のぼんやりした眺めです。チケットを解決すると、その前方の霧が晴れ、今や仕様化可能になったものが新しいチケットに卒業します — 目的地への道が明確になりチケットが残らなくなるまで、1 つずつ。

マップの **Not yet specified** セクションは、そのぼんやりした眺めを書き留める場所です: 疑わしい質問、後で再訪する領域。目的地_に向かう_未発見のフロンティアです — ここにあるものはすべて対象内ですが、チケットにするにはまだ鋭くありません。眺めが許す限り緩く、または完全に書きます。これは取り組みの行き先を読むコラボレーターへの道標も兼ねます。

**霧かチケットか?** テストは、質問を今すぐ正確に述べられるかどうかです — 今すぐ回答できるか_ではありません_。

- **チケットにするのは** 質問がすでに鋭いとき — ブロックされていてまだ行動できなくても。
- **Not yet specified にするのは** まだそれほど鋭く表現できないとき。霧をチケット大のピースに先取りしてスライスしないでください: それはチケットより粗く、1 つのパッチがフロンティアに到達したときいくつかのチケットに卒業するかもしれず、あるいは 1 つも卒業しないかもしれません。

**Not yet specified** は、すでに決定されたもの (Decisions so far)、すでにライブのチケットであるもの、対象外のもの (次のセクション) を除外します。

## 対象外

霧は目的地_に向かって_しか立ちこめません。目的地はスコープを固定するため、それを超える作業は**対象外**です — それは霧ではなく、**Not yet specified** に属しません。マップ上に独自の **Out of scope** セクションを持ちます: _この_取り組みから意識的に除外した作業です。鋭さではなくスコープが、それをここに置きます。

対象外の作業は決して卒業しません — フロンティアは目的地で止まります — したがって、それは目的地が引き直された場合にのみ戻り、そのときも再開ではなく新しい取り組みとして戻ります。

何かを対象外と判断することはスコーピング行為であり、ルート上の一歩ではありません。既に存在するチケットが目的地を超えていると判明した場合 — 地図作成中に誤ってスコープ内に入れた、または解決によって露呈した — は**クローズし** (クローズしたチケットは明確にフロンティア外です)、**Out of scope** セクションに 1 行残します: 要約と対象外の理由、クローズしたチケットへのリンク。それは実際に歩いたルートを記録する **Decisions so far** には留まりません — スコープ境界はルート上の一歩ではありません。

## 呼び出し

2 つのモード。どちらの場合も、**セッションごとに複数のチケットを解決してはいけません** — リサーチチケットは例外です。

### マップを描く

ユーザーが大まかなアイデアで呼び出します。

1. **目的地に名前を付ける。** `/grilling` と `/domain-modeling` のセッションを実行して、このマップが進む先 — 仕様、決定、または変更 — を確定します。目的地はスコープを固定するので、最初に確定します。
2. **フロンティアをマッピングする。** 今度は**幅優先**で再びグリリングします: 1 つのスレッドを深く掘るのではなく、空間全体に広がり、オープンな決定と今取れる最初の一歩を表面化します。**霧が表面化しない場合** — 目的地への道がすでに明確で、旅全体が 1 セッションに収まるほど小さい — マップは不要です。止めて、どう進めたいかユーザーに尋ねます。
3. **マップを作成します** (ラベル `wayfinder:map`): Destination と Notes を記入し、Decisions-so-far は空、霧は **Not yet specified** にスケッチします。qtk CLI の場合: `bunx qtk plan create "目的地の名前" -d "要約" --status in-progress` でマップを作成し、plan の本文に Destination / Notes / Decisions so far / Not yet specified / Out of scope セクションを Markdown で書きます (`wayfinder:map` タグは plan ではなく関連 issue に付与するか、plan の description に明記します)。
4. **今仕様化できるチケットを** マップの子イシューとして作成します — その後**2 回目のパス**でブロッキングエッジを配線します (イシューは互いを参照する前に ID が必要です)。配線はそれらをフロンティアとブロック済みに仕分けます。まだ仕様化できないものはすべて霧 — **Not yet specified** セクション — に留まります。qtk CLI の場合: `bunx qtk issue create "チケットタイトル" -d "質問" --tag wayfinder:research` で作成し、2 回目のパスで `bunx qtk issue edit <ID> --dep <ブロッカーID>` でブロッキングエッジを配線します。
5. **リサーチサブエージェントを起動します。** 作成した各 `research` チケットについて、`/research` サブエージェントを並行して起動して解決させ、その調査結果をチケットからのコンテキストポインタ付きの使い捨て `research/<name>` ブランチに取り込みます。qtk CLI の場合: 各 research チケットを `bunx qtk issue claim <ID>` でクレームしてからサブエージェントを起動します。
6. 止めます — 地図作成は 1 セッション分の作業であり、何も手で解決しません。

### マップを消化する

ユーザーがマップ (URL または番号) で呼び出します。チケットは**任意**です — ない場合は、ユーザーではなくあなたが次の決定を選びます。

1. **マップ**をロードします — 低解像度ビューであり、すべてのチケットボディではありません。
2. チケットを選びます。ユーザーが指名した場合はそれを使います。そうでなければ、順番で最初のフロンティアチケットを取ります。**クレームします**: 作業の前に自分自身にアサインします。qtk CLI の場合: `bunx qtk issue list --ready` でフロンティアを取得し、`bunx qtk issue claim <ID> --as "<名前>"` でクレームします。
3. 解決します — **必要に応じてズームします**: 関連するまたはクローズしたチケットの完全なボディをオンデマンドで取得し、`## Notes` ブロックが指名するスキルを呼び出します。疑わしい場合は `/grilling` と `/domain-modeling` を使用します。
4. 解決を記録します: 回答を**解決コメント**として投稿し、イシューを**クローズ**し、マップの Decisions-so-far に**コンテキストポインタを追記**します。qtk CLI の場合: `bunx qtk issue edit <ID> --comment "回答" --status done` でチケットを解決し、plan の本文を更新して Decisions-so-far に行を追記します。
5. 新しく表面化したチケットを追加し (作成してから配線)、回答が仕様化可能にした霧を卒業させ、卒業した各パッチを **Not yet specified** から消して、新しいチケットとしてのみ存在させます。回答がチケット — これまたは他 — が目的地を超えていることを明らかにした場合は、ルート上で解決するのではなく**対象外と判断**します。決定がマップの他の部分を無効化する場合は、それらのチケットを更新または削除します。

ユーザーはアンブロックされたチケットを並行して実行できるため、他のセッションが同時にトラッカーを編集していることを想定します。
