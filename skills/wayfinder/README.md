## 何をするスキルか

`wayfinder` は、1つのエージェント[セッション](https://www.aihero.dev/ai-coding-dictionary/session)に大きすぎる作業 — **目的地**は名前を付けられるがルートはまだ見えないアイデア — を受け取り、イシュートラッカー上の**決定チケット**の共有**地図**として描き、道が明確になるまでそれらを一度に1つ解決します。

計画しますが、実行しません。すべてのチケットは、実行するビルドのスライスではなく、解決が決定である質問を保持し、地図は、誰かが行って物を構築する前に決めるものが何も残っていないときに完成します。その単一のルールが wayfinder チケットを普通の実装[チケット](https://www.aihero.dev/ai-coding-dictionary/ticket)から分離するものであり、エージェントが最も頻繁に破るルールです。地図がクリアされると、wayfinder はハンドオフします。コードに進み続けません。

## いつ使うか

`/wayfinder` と入力して起動します — [エージェント](https://www.aihero.dev/ai-coding-dictionary/agent)は自分からは使いません。

セットの中で最も重く密度の高いフローなので、トリガーは狭いです: 作業は本当に1つのエージェントセッションが保持できるより大きく、目的地へのルートはぼんやりしていなければなりません。分割はクリーンです: 単一セッション計画には `/grill-with-docs`、複数セッション計画には `/wayfinder`。

| 目の前にあるもの | 実行するもの |
| --- | --- |
| 1回の座りで決着できるよくスコープされたフィーチャー | [grill-me](https://aihero.dev/skills-grill-me)、またはコードベースがあるときは [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| グリーンフィールドプロジェクト、または多くのセッションにまたがるビルドで、ルートがまだ不明確 | `/wayfinder` |
| 決定がすでに終わったスレッド | [to-spec](https://aihero.dev/skills-to-spec) — 地図をまっすぐスキップ |
| クリアされた wayfinder 地図 | [to-spec](https://aihero.dev/skills-to-spec)、それから [to-tickets](https://aihero.dev/skills-to-tickets) と [implement](https://aihero.dev/skills-implement) |
| すでに大きくなりすぎた既存セッション | 「`/wayfinder` にハンドオフ」と言う — [handoff](https://aihero.dev/skills-handoff) が地図への橋でもあり、地図からの橋でもある |

グリーンフィールドは要件ではありません。Wayfinder はレガシーや半構築のコードベースで日常的に使われ、そこでおそらくより鋭いです。霧の多くが「ここで何がすでに真か」であって「何をすべきか」ではないからです。

## 前提条件

地図とそのチケットはリポジトリのイシュートラッカーに住むので、wayfinder には [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) が敷くトラッカー配線が必要です。そのステップは、地図、その子チケット、ブロッキングエッジ、フロンティアクエリが GitHub、GitLab、またはローカル markdown でどう表現されるかを説明する「Wayfinding operations」セクションを書きます。Wayfinder は固定パスではなく、`CLAUDE.md` / `AGENTS.md` のポインタを通じてそのドキュメントを解決します。トラッカーがまったく設定されていなければ、ローカル markdown ファイルにフォールバックします。

トラッカーは飾りではありません。ブロッキングは、トラッカー自身の UI でフロンティアを視覚的にレンダリングするものです。ネイティブの依存リンクのないトラッカー — たとえば自己ホストの Gitea — は wayfinder を地図テキストからブロッカーを推測するよう劣化させますが、それは機能しますが、より密接な監督が必要です。

## 地図、霧、フロンティア

**地図**は `wayfinder:map` とラベル付けされた単一のイシューです。そのチケットは子イシューです。それは**インデックスであり、ストアではありません** — 決定は正確に1つの場所、そのチケットに住み、地図はそれを要約してリンクするだけです。セッションは地図を低解像度でロードし、オンデマンドで個々のチケットにズームします。それが、すべてのセッションがその全履歴を支払うことなく地図が成長し続けられるようにするものです。

4つのものが地図に住みます:

- **目的地** — この地図の終わりに達することがどう見えるか。それを名指しすることがチャーティングの最初の行為で、どのチケットも存在する前に。目的地が、すべてのチケットが測定されるスコープを固定するからです。
- **これまでの決定** — クローズしたチケットごとに1行、それぞれが詳細が実際に住む場所にリンク。
- **まだ指定されていない** — **戦争の霧**。来ると言えるがまだ鋭く表現できない決定。霧とチケットのテストは、その質問を*今*正確に述べられるかどうかであり、答えられるかどうかではありません。チケットを解決すると、その前の霧が晴れ、今や指定可能になったものを新しいチケットに卒業させます。
- **スコープ外** — 目的地を超えたと裁定された作業。霧は目的地に*向かって*だけ集まるので、スコープ外の作業はクローズされ、決して卒業しません。

**フロンティア**はオープンで、ブロックされておらず、請求されていないチケット — 既知の縁。セッションは作業をする前に自分自身にチケットを割り当てることで請求するので、割り当て先*が*請求であり、並行セッションはそれをスキップします。チケットは全体を通して名前で参照され、裸の `#42` では決してありません。イシュー番号の壁はナレーションで判読不能です。

## 4つの決定チケットタイプ

すべてのチケットは `wayfinder:<type>` ラベルを持ち、**[HITL](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)** — 自分のために話す人間と作業される — または **[AFK](https://www.aihero.dev/ai-coding-dictionary/afk)** — エージェントだけで駆動される — のどちらかです。HITL チケットはライブのやり取りを通じてのみ解決します。自分の [grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) 質問に自分で答えるエージェントはそれを壊しています。

| タイプ | モード | 使うとき | 解決されるもの |
| --- | --- | --- | --- |
| `grilling` | HITL | デフォルト。質問は話し合うことで決着できる。 | 新しいセッションでの [grilling](https://aihero.dev/skills-grilling) プラス [domain-modeling](https://aihero.dev/skills-domain-modeling) |
| `prototype` | HITL | 「これはどう見えるべきか」または「これはどう振る舞うべきか」 — 話し合いが決着できない質問。 | [prototype](https://aihero.dev/skills-prototype)。構築されたアーティファクトがアセットとしてチケットからリンクされる |
| `research` | AFK | 作業ディレクトリの外の事実が決定をブロックしている。 | チャーティング時に発火され、`research/<name>` ブランチで並列に焼き尽くされる [research](https://aihero.dev/skills-research) [サブエージェント](https://www.aihero.dev/ai-coding-dictionary/subagent) |
| `task` | どちらか | 決めるものはないが、手動作業が決定をブロックする — アクセスのプロビジョニング、サービスの申し込み、形が見えるようにデータを動かす。 | できるところはエージェント単独、そうでなければ人間のための正確なチェックリスト |

`task` は*する*唯一のタイプであり、決定をブロック解除することで居場所を稼ぎます — 目的地の一部を届けることで決してありません。これは実際に最も頻繁に間違って行われるタイプです: エージェントがそれを実装ステップとして解釈し、地図の中で製品コードを書き始めます。

Research は*セッションごとに1チケット*の唯一の例外です。

## よくある質問

**これは `/grill-with-docs` とどう違う? どちらから始めるべき?**

プロジェクトサイズではなくセッション数。`/grill-with-docs` は単一セッション計画で、wayfinder は複数セッション計画です。全体を1つの会話で保持できるなら、grilling がより安くて良いツールであり、そのケースでは wayfinder は本当に遅くて密度が高い。定着したコミュニティの短縮形: wayfinder は作業が単一セッションに収まらない場合にのみ意味をなす。これは群を抜いて最もよく聞かれる wayfinder の質問であり、説明があなた自身のタスクがその線上でどこに座るかを教えてくれないため、聞かれ続けます — セッション数を自分で判断しなければなりません。

**「目的地」を求めるとき、それはこのセッションの終わりを意味するか、それともすべての終わり?**

地図全体 — 全体の地図の目的地であり、最初のセッションだけではありません。wayfinder は定義上マルチセッションツールなので、質問は曖昧に読めます。セッションスコープの答えは決して意味をなしません。典型的な目的地は、ハンドオフする[仕様](https://www.aihero.dev/ai-coding-dictionary/spec)、計画が始まる前にロックする決定、概念実証、またはデータマイグレーションのようなその場で行う変更です。

**地図がクリアされた。なぜまだ `/to-spec` と `/to-tickets` が必要なの — wayfinder がすでに仕様を書き、チケットを作ったのでは?**

いいえ。Wayfinder のチケットは決定チケットであり、地図が閉じる頃にはそれらもすべて閉じています。残るのはリンクされた決定でいっぱいの地図であり、それはビルド計画ではありません。[to-spec](https://aihero.dev/skills-to-spec) はそれらのリンクされた決定を1つの仕様に崩壊させます — `/to-spec #<map_issue>` — そして [to-tickets](https://aihero.dev/skills-to-tickets) はそれをトレーサーバレット実装チケットに切ります。地図を [implement](https://aihero.dev/skills-implement) に直接ループすると崩壊をスキップし、リンクされた詳細を捨てます。作業が本当に小さかった場合にのみ実装に直接行ってください。人々は短縮パイプラインを実行して機能すると報告しています。2つの追加ステップは、レビュアーや同僚が読める明示的な仕様アーティファクトを買います。それは一人でやらないほど重要になります。

**エージェントが wayfinder セッションの途中で本番コードを書き始めた。**

このスキルで最も報告される失敗で、背後に本当の穴があります。Wayfinder の「計画、実行しない」デフォルトは地図の**Notes**でオーバーライドできます — しかし Notes はエージェントによって書かれるので、制約とその免除は、制約された当事者が所有する同じファイルに住みます。あるユーザーは、エージェントが自分の Notes に「this map carries execution」と書くのを見て、後のセッションでそれを自分自身のライセンスとして読み戻し、ライブサーバー上に構築しました。「私はデフォルトを意味していた」に対するスキル内のハードストップはありません。あるまで: 自分がチャートしなかった地図の Notes を読み、実装を自分のセッションに保ち、ビルドのスライスのように見える `wayfinder:task` をタイプミスとして扱ってください。

**27チケットをチャートしたが、13番目に到達する頃には残りはもはや意味をなさなかった。**

実在の繰り返し報告される結果で、フィールドレポートからの逐語です。Wayfinder のデフォルトの本能は包括的に計画することであり、後のチケットが以前のチケットが無効化する仮定の上に乗る地図は、スキルが非難されるウォーターフォールの罠そのものです。2つのことがそれに押し返します。地図を製品全体ではなく境界のある目的地にスコープする — 実践者は一貫して、1つの定義されたエピックにスコープされた地図は、広がる「implement V1」より良く振る舞うと報告し、そもそも非常に大きなものを計画することは目標ではありません — 小さな増分を出荷することが。そして[プロトタイプ](https://www.aihero.dev/ai-coding-dictionary/prototyping)を積極的に: ルートが現在のままである理由は、実装がそれに依存する前に不確実性が安い具体的なアーティファクトによって洗い出されるからです。Wayfinder は「planmaxxing」ではなく「prototypemaxxing」です。

**いくつかのチケットを並列で作業できますか?**

フロンティアは何が取れるかを見せるために作られ、ブロッキングエッジは並列作業が紙の上で安全であるためにそこにあります。実際には一度に1つがより安全なデフォルトです。一度に2つの grilling チケットを扱うユーザーは、別のセッションでちょうど答えた質問を1つのセッションで聞かれます。セッションが[コンテキスト](https://www.aihero.dev/ai-coding-dictionary/context)を共有しないからです。プロトタイプチケットにも既知のギャップがあります: エージェントが3つの UI バリエーションを構築し、自分で1つを選び、チケットを閉じるのが報告されています — 選択はあなたが行うものであり、スキルは現在それを十分に大声で言っていません。並列で実行するなら、先に依存グラフを自分でレビューしてください。

**GitHub Issues を使わなければならない?**

いいえ — どのイシュートラッカーでも機能します。GitHub が最もサポートされたパスです。ネイティブのサブイシューとブロッキング関係が、地図を開かずにフロンティアを見えるようにするからです。GitLab、Linear、Jira、ローカル markdown はすべて使われます。2つの正直な注意。ネイティブブロッキングのないトラッカーは、依存グラフがテキストから推測され、手動修正が必要です。そしてローカル markdown はアーティファクトをあなたのリポジトリに置きますが、それは推奨されません: この材料をリポジトリに保存すると、偶発的な永続化につながる傾向があります。オープンソースのメンテナーは反対の問題に当たります — エージェント生成の計画チケットで埋まる公開トラッカー — そしてとにかくローカル markdown を選ぶ傾向があります。

**grilling は疲れる。すべての質問が3段落ある。**

これは wayfinder に関する最も鋭い生きた不満であり、解決されていません。あるユーザーが与えた分解: 冗長さ自体が決定疲れを引き起こし、長さが*なぜ*質問がされるのかを剥ぎ取るので、地図が長くなるにつれて決定から決定への連鎖を失います。冗長さはスキルの特性ではなく、現在の[モデル](https://www.aihero.dev/ai-coding-dictionary/model)セットの特性のように見え、修正は着地していません。流通している実践者の緩和策: より低い[推論努力](https://www.aihero.dev/ai-coding-dictionary/effort)で実行し、グローバル `CLAUDE.md` に平易な言葉の指示を置く。ここで本当に考えることを期待してください — wayfinder があなたに要求する思考の量は欠陥ではなく、それが何のためにあるかのほとんどです。

**すでに閉じた決定が間違っていたと判明した。古いチケットを編集するか、新しいものを作るか?**

公式のガイダンスはなく、エージェントの本能は役に立たない: それは悪い決定を挑戦するよりもそれを中心に設計する傾向があるので、手動で操縦しなければなりません。機能するのは wayfinder に何が変わったかを率直に伝えることです — 地図を更新し、影響を受けるチケットを修正し、すでにクローズしたものにコメントします。途中でのスコープ変更は回復可能です。*変更するように設計された*地図はスコーピングのスメルです。

**`decision-mapping` はどこへ行った?**

それがこのスキルで、v1.1 で `wayfinder` にリネームされ `/wayfinder` として起動されます。「Decision map」は専門用語であり、4つのチケットタイプのうち本当に決定であるのは1つだけなので、不正確でもありました。リフレームはスキルに1つの一貫した語彙 — 目的地、戦争の霧、フロンティア、地図 — を、発明された用語を上に重ねる代わりに与えました。ただし単位は「decision」という言葉を保持しました: wayfinder のチケットがそう呼ばれるのは、まさにそれを実装チケットとして読むのを止めるためです。

## うまく機能しているなら

- 目的地が単一のチケットが存在する前に書き下ろされ、合意される。
- すべてのオープンチケットが質問として読める。「X を構築する」と読むチケットは、タイプミスか、地図の下流に属する。
- トラッカーを見て、地図を開かずにどのチケットが取れるか見える — それがネイティブブロッキングを通じてレンダリングされるフロンティア。
- セッションが1つのチケットを解決し、解決コメントとして答えを投稿し、閉じ、地図の *Decisions so far* に1行残す。それから止まる。
- **まだ指定されていない**が時間とともに縮む。チケットに卒業する霧のパッチが、両方の場所に住むのではなくそのセクションから消える。
- 開幕の幅優先 grill がまったく霧を出さないとき、スキルは止まり、作業が地図をスキップするほど小さいと伝える。
- 地図を終えるセッションが、プルリクエストではなく仕様に向けてあなたを導く。

## どこに位置づくか

`wayfinder` はデフォルトの正面玄関ではなく**状況的オンランプ**です。grill 主導のアイデア → 出荷チェーンが依然としてほとんどの作業の開始点であり、wayfinder はアイデアが1セッションに収めるには大きすぎるときに登るもので、クリアされた地図は構築するのではなくハンドオフするので、[to-spec](https://aihero.dev/skills-to-spec) でそのチェーンに合流します。

下では、それはほとんど wayfinder のスケジューリングを着た他のスキルです: [grilling](https://aihero.dev/skills-grilling) と [domain-modeling](https://aihero.dev/skills-domain-modeling) がデフォルトのチケットタイプを解決し、[prototype](https://aihero.dev/skills-prototype) が話し合いができないチケットを解決し、[research](https://aihero.dev/skills-research) はその読みがあなたのセッションに決して着地しないようにサブエージェントとして実行されます。[handoff](https://aihero.dev/skills-handoff) は出入りの橋です — 自分を超えて成長した会話から地図に入り、セッション中にサイドクエストが現れたときに地図から出る。他の何かについては、[ask-matt](https://aihero.dev/skills-ask-matt) がセット全体をルーティングします。
