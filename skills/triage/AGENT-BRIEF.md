# エージェントブリーフを書く

エージェントブリーフとは、イシューや PR が `ready-for-agent` に移動したときに GitHub のイシューまたは PR に投稿される構造化コメントです。AFK エージェントが作業のよりどころとする権威ある仕様です。元のボディと議論はコンテキストであり、エージェントブリーフがコントラクトです。

ブリーフは**エージェントが何をすべきか**を述べます。これは両方のサーフェスに及びます: イシューの場合はゼロから変更を構築すること、PR の場合は*既存の差分*に対して残っていること — 仕上げる、ギャップを埋める、レビュー指摘に対応する — です。原則はどちらの場合も同じで、以下の PR の例が違いを示しています。

## 原則

### 正確さよりも耐久性

イシューは `ready-for-agent` に数日または数週間置かれるかもしれません。その間にコードベースは変わります。ファイルがリネーム・移動・リファクタリングされても役に立ち続けるようにブリーフを書きます。

- **すべきこと** インターフェース、型、振る舞いのコントラクトを記述する
- **すべきこと** エージェントが探す・修正すべき具体的な型、関数シグネチャ、設定の形に名前を付ける
- **すべきでないこと** ファイルパスを参照する — すぐに古くなる
- **すべきでないこと** 行番号を参照する
- **すべきでないこと** 現在の実装構造が変わらずに残ることを前提にする

### 手順ではなく振る舞い

システムが**何を**すべきかを記述し、**どうやって**実装するかは記述しません。エージェントはコードベースを新しく探索し、自分で実装の決定を下します。

- **良い:** 「`SkillConfig` 型は、`CronExpression` 型のオプショナルな `schedule` フィールドを受け入れるべきである」
- **悪い:** 「src/types/skill.ts を開いて、42 行目に schedule フィールドを追加して」
- **良い:** 「ユーザーが引数なしで `/triage` を実行すると、注意が必要なイシューの要約を見られるべきである」
- **悪い:** 「メインハンドラー関数に switch 文を追加して」

### 完全な受け入れ基準

エージェントはいつ完了するかを知る必要があります。すべてのエージェントブリーフは、具体的でテスト可能な受け入れ基準を持たなければなりません。各基準は独立して検証可能であるべきです。

- **良い:** 「`gh issue list --label needs-triage` を実行すると、初期分類を通過したイシューが返る」
- **悪い:** 「トリアージが正しく動作するべき」

### 明確なスコープ境界

何が対象外かを明示します。これによりエージェントが金メッキしたり、隣接機能について推測したりするのを防ぎます。

## テンプレート

```markdown
## Agent Brief

**カテゴリ:** bug / enhancement
**要約:** 何が起こる必要があるかの 1 行の説明

**現在の振る舞い:**
今何が起こるかを記述します。バグの場合は、これが壊れた振る舞いです。
拡張機能の場合は、機能が構築される前提となる現状です。

**望ましい振る舞い:**
エージェントの作業完了後に何が起こるべきかを記述します。
エッジケースとエラー条件について具体的にします。

**主要なインターフェース:**
- `TypeName` — 何をなぜ変更する必要があるか
- `functionName()` の戻り値の型 — 現在返すもの vs 返すべきもの
- 設定の形 — 必要となる新しい設定オプション

**受け入れ基準:**
- [ ] 具体的でテスト可能な基準 1
- [ ] 具体的でテスト可能な基準 2
- [ ] 具体的でテスト可能な基準 3

**対象外:**
- このイシューで変更・対応すべきではないもの
- 関連するように見えるが別物の隣接機能
```

## 例

### 良いエージェントブリーフ (バグ)

```markdown
## Agent Brief

**カテゴリ:** bug
**要約:** スキル説明の切り詰めが単語の途中で切れ、壊れた出力を生む

**現在の振る舞い:**
スキル説明が 1024 文字を超えると、単語の境界に関係なく正確に
1024 文字で切り詰められます。そのため説明が単語の途中で
終わります (例: "Use when the user wants to confi")。

**望ましい振る舞い:**
切り詰めは 1024 文字より前の最後の単語境界で区切り、
切り詰めを示す "..." を追加するべきです。

**主要なインターフェース:**
- `SkillMetadata` 型の `description` フィールド — 型の変更は不要だが、
  それを埋める検証・処理ロジックが単語境界を尊重する必要がある
- SKILL.md の frontmatter を読み、説明を抽出する任意の関数

**受け入れ基準:**
- [ ] 1024 文字未満の説明は変更されない
- [ ] 1024 文字を超える説明は 1024 文字より前の最後の単語境界で切り詰められる
- [ ] 切り詰められた説明は "..." で終わる
- [ ] "..." を含む合計の長さは 1024 文字を超えない

**対象外:**
- 1024 文字の上限自体を変更すること
- 複数行の説明のサポート
```

### 良いエージェントブリーフ (拡張機能)

```markdown
## Agent Brief

**カテゴリ:** enhancement
**要約:** 拒否された機能リクエストを追跡するための `.out-of-scope/` ディレクトリのサポートを追加する

**現在の振る舞い:**
機能リクエストが拒否されると、イシューは `wontfix` ラベルとコメント付きで
クローズされます。決定や理由の永続的な記録はありません。
将来の同様のリクエストでは、メンテナが以前の議論を記憶または検索する
必要があります。

**望ましい振る舞い:**
拒否された機能リクエストは、決定、理由、機能をリクエストしたすべての
イシューへのリンクを記録する `.out-of-scope/<concept>.md` ファイルに
文書化されるべきです。新しいイシューのトリアージ時に、これらのファイルが
一致するかチェックされるべきです。

**主要なインターフェース:**
- `.out-of-scope/` の Markdown ファイル形式 — 各ファイルは
  `# Concept Name` 見出し、`**Decision:**` 行、`**Reason:**` 行、
  イシューリンク付きの `**Prior requests:**` リストを持つべき
- トリアージワークフローは早期にすべての `.out-of-scope/*.md` ファイルを
  読み、受信したイシューを概念の類似性で照合すべき

**受け入れ基準:**
- [ ] 機能を wontfix としてクローズすると、`.out-of-scope/` のファイルが作成・更新される
- [ ] ファイルには決定、理由、クローズしたイシューへのリンクが含まれる
- [ ] 一致する `.out-of-scope/` ファイルがすでに存在する場合、新しいイシューは
      重複を作成せずにその "Prior requests" リストに追記される
- [ ] トリアージ中に、既存の `.out-of-scope/` ファイルがチェックされ、
      新しいイシューが以前の拒否に一致するときに表面化される

**対象外:**
- 自動マッチング (一致の確認は人間)
- 以前拒否された機能の再オープン
- バグレポート (`.out-of-scope/` にいくのは拡張機能の拒否のみ)
```

### 良いエージェントブリーフ (PR)

PR の場合、"Current behavior" は差分の状態を記述し、ブリーフはゼロから構築するのではなく仕上げる・修正することをエージェントに求めます。

```markdown
## Agent Brief

**カテゴリ:** enhancement
**要約:** `triage list` に対するコントリビューターの `--json` 出力フラグを仕上げる

**現在の振る舞い:**
PR はイシューリストを JSON にシリアライズする `--json` フラグを追加します。ハッピー
パスは動作し、差分はプロジェクトのコマンド構造に一致しています。2 つのギャップが
残っています: エラーはまだ人間向けテキストで出力され (JSON ではない)、新しいフラグには
テストのカバレッジがありません。

**望ましい振る舞い:**
`--json` では、エラーを含むすべての出力が stdout 上の整形式の JSON であり、
コマンドの終了コードは変更されません。既存の人間可読な出力は
フラグがない場合にそのまま保たれます。

**主要なインターフェース:**
- コマンドのエラーパスは、`--json` の下でプレーンテキストのエラーではなく
  `{ "error": string }` を出力すべき
- PR がすでに追加した既存のシリアライザーを再利用し、2 つ目を導入しない

**受け入れ基準:**
- [ ] `triage list --json` は成功・エラーの両方のケースで有効な JSON を出力する
- [ ] 終了コードは非 JSON コマンドと一致する
- [ ] テストが `--json` の成功出力と 1 つのエラーケースをカバーする
- [ ] デフォルト (非 JSON) の出力はバイト単位で変更されない

**対象外:**
- 他のコマンドに `--json` を追加すること
- PR がすでに定義した成功ペイロードの JSON の形を変更すること
```

### 悪いエージェントブリーフ

```markdown
## Agent Brief

**要約:** トリアージのバグを修正する

**何をするか:**
トリアージのものが壊れています。メインファイルを見て修正してください。
150 行目あたりの関数に問題があります。

**変更するファイル:**
- src/triage/handler.ts (150 行目)
- src/types.ts (42 行目)
```

これが悪い理由:
- カテゴリがない
- 曖昧な説明 (「トリアージのものが壊れている」)
- 古くなるファイルパスと行番号を参照している
- 受け入れ基準がない
- スコープ境界がない
- 現在と望ましい振る舞いの説明がない
