## 何をするスキルか

`triage` はプロジェクトのトラッカー上のイシューを処理し、それぞれを**トリアージロール**の小さな状態機械 — カテゴリロールと状態ロール — を通じて動かし、エージェント対応のブリーフ、報告者への具体的な質問、または理由を記録したクローズイシューのいずれかを残します。

**あなたが作成していない**イシューのためだけです。生のバグ報告、届いたフィーチャーリクエスト、予告なく到着した外部プルリクエスト — 外部から、報告者が残した形のままトラッカーに着地した作業。[to-tickets](https://aihero.dev/skills-to-tickets) が生成した[チケット](https://www.aihero.dev/ai-coding-dictionary/ticket)は構成的にエージェント対応であり、それらに `triage` を実行するのは良くて無駄な作業です。ルールは平坦です: `/triage` はあなたが自分で作成したイシューではなく、届いたイシューのためだけです。

手でのラベリングと区別する2つ目のこと: 推奨して待ちます。カテゴリと状態の呼び出しを理由付きで、コードベースで見つけたものと一緒に伝え、あなたが指示するまで何も適用しません。

## いつ使うか

`/triage` と入力して、欲しいものを平易な言葉で説明して起動します — [エージェント](https://www.aihero.dev/ai-coding-dictionary/agent)は自分からは使いません。「私の注意を必要とするものをすべて見せて」、「#42 を見てみよう」、「#42 を ready-for-agent に動かして」。

| あなたが持っているもの | 行き先 |
| --- | --- |
| 他人からの生の報告でいっぱいのトラッカー | `/triage` |
| 自分自身の粗いアイデア、何も書き下ろしていない | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| [仕様](https://www.aihero.dev/ai-coding-dictionary/spec)に変える確定した会話 | [to-spec](https://aihero.dev/skills-to-spec) |
| エージェント対応チケットに分割する仕様 | [to-tickets](https://aihero.dev/skills-to-tickets) |
| ラベルではなく根本原因を必要とする確認済みバグ | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

## 前提条件

`triage` はイシュートラッカーを読み書きするので、[setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) が最初にそのトラッカーとラベル語彙を設定している必要があります。下のロール名は**正規**です。トラッカーのラベル文字列は異なるかもしれませんが、マッピングはセットアップが提供するものです。トラッカーが正規名を正確にすでに使っているなら、マップするものも設定するものもありません。

トラッカー設定は、外部プルリクエストがリクエスト面として数えられるか、誰が外部と数えられるかも決めます。そのフラグはデフォルトでオフで、もはやセットアップの質問ではありません — PR をスコープに入れたいなら `docs/agents/issue-tracker.md` で切り替えてください。

## 状態機械

トリアージされたすべての項目は、ちょうど1つのカテゴリロールと1つの状態ロールを運んで終わります。2つのカテゴリ: `bug`(何かが壊れている)と `enhancement`(新しいフィーチャーまたは改善)。5つの状態:

| 状態 | 意味 |
| --- | --- |
| `needs-triage` | 評価する必要がある。ラベルのないイシューが通常最初に着地するところ。 |
| `needs-info` | 報告者を待っている。彼らが返信すると `needs-triage` に戻る。 |
| `ready-for-agent` | 完全に指定され、エージェントブリーフが添付されている。[AFK](https://www.aihero.dev/ai-coding-dictionary/afk) エージェントが取れる。 |
| `ready-for-human` | 同じブリーフに加えて、なぜこれを委譲できないか — 判断、外部アクセス、手動テスト。 |
| `wontfix` | 理由を記録してクローズ。 |

それが語彙のすべてであり、「ちょうど1つの状態ロール」不変条件がクエリを単純に保ちます。それはまた[スキル](https://www.aihero.dev/ai-coding-dictionary/skill)の最もリクエストされる領域です: ユーザーは別のイシューにブロックされた指定済み作業のための6番目の状態、将来のトリガーでゲートされる `deferred` 作業、終端の `implemented` 状態を求めてきました。どれも出荷されていません。下の質問を参照してください。

`wontfix` は3方向に分かれ、違いが重要なのは3つのうち1つだけが知識ベースに書くからです:

| 閉じる理由 | 何が起こるか |
| --- | --- |
| すでに実装済み | すでに存在する場所を指すコメント。`.out-of-scope/` には何も書かれない — それは拒否された機能ではなく構築されたフィーチャーであり、そこにファイリングすると重複チェックを汚染する。 |
| 拒否されたバグ | 丁寧な説明、それからクローズ。 |
| 拒否されたエンハンスメント | `.out-of-scope/` のファイル、クローズコメントからリンク、それからクローズ。 |

`.out-of-scope/` は拒否された**概念**ごとに1つの markdown ファイルで、イシューごとではありません。データベース行ではなく短い設計文書として書かれます: 何が拒否されたか、なぜか、それを求めたすべてのイシュー。`triage` は何かを評価する前にディレクトリ全体を読み、キーワードではなく概念で一致します — 「night theme」は `dark-mode.md` に一致します。一致に当たると、ゼロからリクエストを再審理する代わりに古い決定を表面化し、あなたがまだ同じ気持ちか尋ねます。

## ブリーフの前に検証

[grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) の前に、`triage` は主張が実際に成立するかチェックします。バグの場合、報告者のステップから再現します。PR の場合、ブランチをチェックアウトして関連テストを実行します。それから3つのうちどれが起こったかを報告します: コードパス付きで確認、再現できず、または試すのに十分な詳細がない — それがそれ自体最も強い `needs-info` シグナルです。

同じパスでコードベースに対してさらに2つのチェックを実行します — **冗長性**(これはすでに実装されているか、報告者の言い回しではなくドメイン概念で検索)と**以前の拒否**(`.out-of-scope/` がすでにノーと言っているか)。どちらも安く、当たると `wontfix` を生成します。

そのすべてが1つのアーティファクトを良くするために存在します: **エージェントブリーフ**、イシューが `ready-for-agent` に動いたときに投稿される構造化コメント。投稿されると、ブリーフが契約であり、元の報告は文脈だけです。ブリーフは正確ではなく**耐久性**があるように書かれます。イシューは下のコードが動きながら数週間 `ready-for-agent` に座り得るからです。そのため型、シグネチャ、振る舞いの契約を名指しし、ファイルパスや行番号は決して名指ししません。確認された再現は、推測よりもはるかに強いブリーフを作ります。

## PR はコードが添付されたイシュー

トラッカーが外部プルリクエストをリクエスト面として扱う場合、それらは同じ機械を通過します — 同じカテゴリ、同じ状態、同じ遷移。状態は差分に対して読むだけです: `ready-for-agent` はブリーフが添付され、エージェントがコードの次のステップを取るべきであることを意味し、`ready-for-human` は人間がマージする準備ができていることを意味します。PR のブリーフは、既存の差分に残っていることを説明し、ゼロから物を構築する方法ではありません。

発見は*外部*PR のみを表面化します。コラボレーターの進行中のブランチはトリアージ作業ではないからです。そのフィルターは発見専用です — PR を明示的に名指しすると、書いた人が誰でもトリアージされます。1つの粗いエッジ: GitHub テンプレートの外部 PR リストコマンドは `gh pr list` に `gh` が公開しない `authorAssociation` フィールドを求めるので、書かれたコマンドはそのまま失敗します([#468](https://github.com/mattpocock/skills/issues/468))。

## よくある質問

**`/to-spec` と `/to-tickets` を実行し、今それらのチケットがトリアージされずに座っている。それらに `/triage` を実行する?**

いいえ。それらはすでにエージェント対応です — `to-tickets` は公開するときに `ready-for-agent` ラベルを適用し、まさに AFK ランナーが追加のパスなしでそれらを拾うためです。これに当たったユーザーは仕様フローを実行し、出力に `needs-triage` を見て、AFK ランナーがすべてを無視していることに気づきました。`triage` は外部から届く作業のオンランプです。仕様フローはあなたが発信する作業のレーンです。それらは `ready-for-agent` で出会い、それより前では出会いません。

**`to-spec` → `to-tickets` → `implement` フローができた今、`triage` はまだ関連しますか?**

インバウンド作業がある場合のみ。`triage` はその背骨より前からあり、別の仕事をします: それは他の人々が提出した報告のレーンです。トラッカーのすべてが自分の計画から出たなら、めったに開かないでしょう。何か公開のものを維持しているか、チームがあなたにバグを提出するなら、それは正面玄関です。主な用途は外部コントリビューターからイシューを受け取るオープンソースリポジトリです。

**エージェントが `ready-for-agent` を適用しようとし、`gh` がラベルは存在しないと言った。**

既知のオープンバグです([#616](https://github.com/mattpocock/skills/issues/616))。`setup-matt-pocock-skills` はラベル語彙を `docs/agents/triage-labels.md` に書きますが、トラッカーにラベルを作成しません。5つの状態ラベルと2つのカテゴリラベルを自分で、一度、`gh label create` またはトラッカーの UI で作成すれば、止まります。イシューからリンクされた未マージのコミュニティ修正ブランチがあります。

**5つの状態では不十分 — blocked、deferred、implemented はどう?**

スキルで最も多く提出されたギャップで、3つの形があります。完全に指定されているが別のイシューのクローズを待っているイシュー([#139](https://github.com/mattpocock/skills/issues/139)) — 報告者の不満は、そこで `ready-for-agent` が「技術的に真」だが誤解を招き、エージェントが拾って壁に当たることでした。意図されているがまだ実行可能でないトリガーゲート付きの将来作業([#297](https://github.com/mattpocock/skills/issues/297))。そして「実装済み、検証待ち」の終端状態で、それがないと AFK ランナーが完了したチケットを再キューできる。Matt は blocked ケースが本物であることに同意し、名前(`blocked` 対 `paused`)は未定です。どれも出荷されていません。人々が使う回避策は、カテゴリの横にリポジトリローカルの追加ラベルで、正規の状態スロットを正直なもので占めておく代償としてスキルがそれを知らないことを支払います。1つのコミュニティ派生はさらに進み、`needs-slicing`、`tracking`、努力ラベルを追加します — それは機能しますが、彼らのものであってスキルのものではありません。

**これは `/diagnosing-bugs` とどう違う?**

ここでの検証ステップは意図的に浅いです — 「これは本当か、おおよそどこに住むか」に答えるのに十分で、根本原因を見つけるためではありません。バグが数分で報告者のステップから再現しないとき、正直な動きは `needs-info`、または今それを追いたいなら [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) です。どちらのスキルのテキストも現在互いについて言及しておらず、あるユーザーがそのシームを見つけ、まだオープンです。

**バックログ全体に向けて実行させられますか?**

頼むことはできますが、何を読むか注意してください。「注意を必要とするものを示す」パスは*選択*を意図した安いリストです — 1つを選ぶと、選んだ1つについて完全な[コンテキスト](https://www.aihero.dev/ai-coding-dictionary/context)を集めます。一度に20のイシューにまたがって実行すると、エージェントが静かにその安いリストを証拠ベースとしてフォールバックし、イシュー本文は返すがコメントは返さないことがあります。あるユーザーはまさにこれに当たりました: 3つのイシューがすでに「already fixed, recommend closing」というコメントを持ち、3つすべてが代わりに新しいエージェントブリーフを得ました。バルクパスが欲しいなら、コメントをイシューごとに読まなければならないと明示的に言ってください。

**Linear や GitHub Issues 以外のもので機能しますか?**

はい — トラッカーは設定であってハードコードされた仮定ではなく、人々は(`linear` CLI 経由の) Linear、GitLab、`.scratch/` の下のプレーンな markdown ファイルに対して実行します。一般的な分割は、イシューと計画に Linear、コードと PR に GitHub です:「issue tracker」と言うスキルは Linear にマップし、「PR」と言うスキルは GitHub にマップします。ローカル markdown トラッカーには、生成されたファイルが受け入れ基準をトップレベルとエージェントブリーフ内の両方に二重に持つことができるオープンテンプレートバグがあります([#200](https://github.com/mattpocock/skills/issues/200))。

## うまく機能しているなら

- 触れるすべての項目がちょうど1つのカテゴリロールと1つの状態ロールで終わる — 決してゼロ、決して2つの競合する状態。
- 理由付きの推奨を与えて止まり、再ラベリングして進むことはしない。
- `ready-for-agent` に何かが到達する前に、バグが再現されるか、PR がチェックアウトされて実行された。
- 書くブリーフが型と振る舞いを名指しし、ファイルパスと行番号を含まない。
- 6ヶ月前に拒否されたリクエストが戻ってきて、新しくトリアージする代わりにそれを言い、古い理由を引用する。
- 投稿するすべてのコメントが `> *This was generated by AI during triage.*` で始まる。

## どこに位置づくか

`triage` はメインチェーンのステップではなく**オンランプ**です。メインフローはあなたが持ったアイデアから実行されます — grill、spec、tickets、implement、review — そして `triage` は代わりに届いた作業の並行レーンです。それは同じ場所で合流します: ブリーフが付いた `ready-for-agent` とラベル付けされたイシューで、[implement](https://aihero.dev/skills-implement) が [to-tickets](https://aihero.dev/skills-to-tickets) のチケットとまったく同じように拾います。リクエストがブリーフできる前に研ぎ澄ましを必要とするとき、`triage` は [grilling](https://aihero.dev/skills-grilling) と [domain-modeling](https://aihero.dev/skills-domain-modeling) を一緒に、一度に1ラウンドの質問で実行し、決定が行われるにつれて `CONTEXT.md` と ADR に着地します。どのレーンにいるか分からないときは、[ask-matt](https://aihero.dev/skills-ask-matt) がルーティングします。
