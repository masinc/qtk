# Triage

プロジェクトのイシュートラッカーのイシューを、少数のトリアージロールからなる状態機械に通します。

このリポジトリが外部プルリクエストをリクエスト面として扱う場合 (イシュートラッカー設定を参照)、トリアージはそれらも対象にします: **PR はコードが添付されたイシューです** — 同じロール、同じ状態、同じ機械で、以下で「PR の場合」と記された若干の違いがあります。裸の `#42` は、トラッカー設定に従ってイシューか PR かに解決します (qtk CLI の場合は `#0042` 形式、4 桁ゼロ埋め)。

トリアージ中にイシュートラッカーに投稿するすべてのコメント・イシューは、次の免責事項で**始めなければなりません**:

```
> *This was generated by AI during triage.*
```

## リファレンスドキュメント

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 耐久性のあるエージェントブリーフの書き方
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` ナレッジベースの仕組み

## ロール

2 つの**カテゴリ**ロール:

- `bug` — 何かが壊れている
- `enhancement` — 新機能または改善

5 つの**状態**ロール:

- `needs-triage` — メンテナが評価する必要がある
- `needs-info` — 報告者からの追加情報を待っている
- `ready-for-agent` — 完全に仕様化されており、AFK エージェントの準備ができている
- `ready-for-human` — 人間による実装が必要
- `wontfix` — 対応しない

PR の場合、同じ状態が添付されたコードに対して解釈されます: `ready-for-agent` はブリーフが添付されておりエージェントが差分の次のステップを取るべきことを意味し、`ready-for-human` は人間がマージできる状態であることを意味します。

トリアージされた各イシューは、カテゴリロールを 1 つと状態ロールを 1 つ正確に持つべきです。状態ロールが競合する場合は、フラグを立てて、他のことをする前にメンテナに尋ねます。

これらは標準的なロール名です — イシュートラッカーで実際に使われるラベル文字列は異なる場合があります。マッピングは提供されているはずです — 提供されていない場合は `/setup-matt-pocock-skills` を実行してください。

状態遷移: ラベルのないイシューは通常、最初に `needs-triage` に移動します。そこから `needs-info`、`ready-for-agent`、`ready-for-human`、または `wontfix` に移動します。報告者が返信すると `needs-info` は `needs-triage` に戻ります。メンテナはいつでもオーバーライドできます — 異常に見える遷移はフラグを立て、進める前に尋ねてください。

## 呼び出し

メンテナが `/triage` を呼び出し、自然言語で何を望むか説明します。リクエストを解釈して行動します。例:

- 「注意が必要なものをすべて見せて」
- 「#42 を見てみよう」(イシューまたは PR)
- 「#42 を ready-for-agent に移動して」
- 「エージェントが拾える準備ができているものは?」

## 注意が必要なものを表示する

イシュートラッカーにクエリし、古い順に 3 つのバケットを提示します。qtk CLI の場合は以下のコマンドでクエリします:

1. **ラベルなし** — 一度もトリアージされていない。`bunx qtk issue list` でタグなしのイシューを確認します。
2. **`needs-triage`** — 評価が進行中。`bunx qtk issue list --tag needs-triage` で取得します。
3. **前回のトリアージノート以降に報告者の活動がある `needs-info`** — 再評価が必要。`bunx qtk issue list --tag needs-info` で取得し、コメント履歴を確認します。

本物のイシュートラッカー (GitHub / GitLab) の場合は、トラッカーのネイティブクエリ機能を使用します。

PR が対象の場合は、外部 PR をこれらのバケットに含め、各行に `[PR]` または `[issue]` のタグを付けます。発見サーフェスは*外部* PR のみを対象にします (誰が外部かを定義するのはトラッカー設定) — コラボレーターの進行中の PR はトリアージ作業ではありません。このフィルタは発見専用です。明示的に指名された PR は著者に関係なく常にトリアージされます。

項目ごとに件数と 1 行の要約を表示します。メンテナに選ばせます。

## 特定のイシューまたは PR をトリアージする

1. **コンテキストを集める。** イシューまたは PR の全体 (ボディ、コメント、ラベル、著者、日付。PR の場合は差分も) を読みます。以前のトリアージノートを解析して、解決済みの質問を再度尋ねないようにします。プロジェクトのドメイン用語集を使ってコードベースを探索し、その領域の ADR を尊重します。コードベースに対して 2 つのチェックを実行します: (a) **冗長性** — リクエストされた振る舞いの既存実装をドメイン概念で検索し (リクエストの文言だけではなく)、どこを調べたか報告します。見つかった場合は、すでに実装されている `wontfix` です (ステップ 5)。(b) **過去の拒否** — `.out-of-scope/*.md` を読み、このリクエストに類似するものを表面化します。

2. **推奨する。** カテゴリと状態の推奨を理由とともに、リクエストに関連する簡潔なコードベースの要約 — すでに実装されているかどうかも含めて — をメンテナに伝えます。指示を待ちます。

3. **主張を検証する。** グリリングの前に、主張が成立するか確認します。バグの場合は、報告者の手順から再現します。PR の場合は、差分が主張することを実際に行うか確認します — チェックアウトし、関連するテストやコマンドを実行します。何が起こったか報告します: 確認 (コードパス付き)、失敗、または詳細不足 (強い `needs-info` シグナル)。確認された検証は、はるかに強力なエージェントブリーフになります。

4. **グリリングする (必要な場合)。** リクエストに肉付けが必要な場合は、`/grilling` と `/domain-modeling` スキルを一緒に実行します — 一度に 1 ラウンドの質問で形を整え、ドメイン用語を研ぎ澄まし、決定が下されるたびに `CONTEXT.md`/ADR をインラインで更新します。

5. **結果を適用する:**
   - `ready-for-agent` — エージェントブリーフのコメントを投稿します ([AGENT-BRIEF.md](AGENT-BRIEF.md))。qtk CLI の場合: `bunx qtk issue edit <ID> --add-tag ready-for-agent --comment "エージェントブリーフ"`
   - `ready-for-human` — エージェントブリーフと同じ構造ですが、委任できない理由 (判断が必要、外部アクセス、設計上の決定、手動テスト) を記します。qtk CLI の場合: `bunx qtk issue edit <ID> --add-tag ready-for-human --comment "ブリーフ"`
   - `needs-info` — トリアージノートを投稿します (以下のテンプレート)。qtk CLI の場合: `bunx qtk issue edit <ID> --add-tag needs-info --comment "トリアージノート"`
   - `wontfix` — クローズし、コメントは*理由*によって異なります。qtk CLI の場合: `bunx qtk issue edit <ID> --add-tag wontfix --status done`:
     - **すでに実装済み** — 変更はコードベースにすでに存在します。どこにあるかを指し示します。`.out-of-scope/` には**書きません** (そのナレッジベースは*拒否された*リクエスト用であり、実装済みのもの用ではありません)。
     - **拒否 (バグ)** — 丁寧な説明をしてからクローズします。
     - **拒否 (拡張機能)** — `.out-of-scope/` に書き、コメントからリンクし、クローズします ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md))。
   - `needs-triage` — ロールを適用します。部分的な進捗がある場合は任意のコメント。qtk CLI の場合: `bunx qtk issue edit <ID> --add-tag needs-triage`

## クイックな状態オーバーライド

メンテナが「#42 を ready-for-agent に移動して」と言った場合は、彼らを信頼してロールを直接適用します。実行しようとしていること (ロール変更、コメント、クローズ) を確認してから行動します。グリリングはスキップします。グリリングセッションなしで `ready-for-agent` に移動する場合は、エージェントブリーフを書くかどうかを尋ねます。qtk CLI の場合: `bunx qtk issue edit 0042 --add-tag ready-for-agent`

## Needs-info テンプレート

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

グリリング中に解決したすべてを「established so far」の下に記録し、作業が失われないようにします。質問は具体的かつ実行可能でなければならず、「詳細情報を提供してください」のようなものではいけません。

## 前回のセッションを再開する

イシューまたは PR に以前のトリアージノートがある場合は、それを読み、報告者が未解決の質問に回答したかを確認し、続行する前に最新の状況を提示します。解決済みの質問を再度尋ねないでください。
