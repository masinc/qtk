# Out-of-Scope ナレッジベース

リポジトリの `.out-of-scope/` ディレクトリは、拒否された機能リクエストの永続的な記録を保存します。2 つの目的があります:

1. **組織の記憶** — 機能が拒否された理由。イシューがクローズされても理由が失われないようにするため
2. **重複排除** — 以前の拒否に一致する新しいイシューが来たとき、再審理する代わりにスキルが以前の決定を表面化できるようにするため

## ディレクトリ構成

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

**概念**ごとに 1 ファイルであり、イシューごとではありません。同じことをリクエストする複数のイシューは 1 つのファイルにまとめられます。

## ファイル形式

ファイルはゆるやかで読みやすいスタイルで書くべきです — データベースのエントリというより、短い設計ドキュメントのように。段落、コードサンプル、例を使って、初めて目にする人にも理由が明確で役立つようにします。

```markdown
# Dark Mode

このプロジェクトはダークモードやユーザー向けのテーマ設定をサポートしません。

## なぜこれが対象外か

レンダリングパイプラインは `ThemeConfig` で定義された単一のカラーパレットを
前提としています。複数のテーマをサポートするには、次のものが必要になります:

- コンポーネントツリー全体を包むテーマコンテキストプロバイダー
- コンポーネントごとのテーマ対応スタイル解決
- ユーザーのテーマ設定の永続化レイヤー

これはプロジェクトのコンテンツ作成への注力と一致しない大きなアーキテクチャ
変更です。テーマ設定は出力を埋め込んだり再配布したりするダウンストリームの
利用者が関心を持つものです。

```ts
// 現在の ThemeConfig インターフェースは実行時の切り替え用に設計されていない:
interface ThemeConfig {
  colors: ColorPalette; // ビルド時に解決される単一のパレット
  fonts: FontStack;
}
```

## Prior requests

- #42 — "Add dark mode support"
- #87 — "Night theme for accessibility"
- #134 — "Dark theme option"
```

### ファイルの命名

概念には短く説明的な kebab-case の名前を使います: `dark-mode.md`、`plugin-system.md`、`graphql-api.md`。ディレクトリを閲覧する人がファイルを開かなくても何が拒否されたか理解できる程度に認識できる名前にします。

### 理由の書き方

理由は実質的であるべきです — 「これを望んでいない」ではなく、なぜなのか。良い理由は次を参照します:

- プロジェクトのスコープや哲学 (「このプロジェクトは X に注力している。テーマ設定はダウンストリームの関心事だ」)
- 技術的制約 (「これをサポートするには Y が必要で、それは我々の Z アーキテクチャと衝突する」)
- 戦略的決定 (「A の代わりに B を選んだのは…」)

理由は耐久性があるべきです。一時的な事情への言及を避けます (「今は忙しすぎる」) — それらは本当の拒否ではなく、先送りです。

## `.out-of-scope/` をチェックするタイミング

トリアージ中 (ステップ 1: コンテキストを集める) に、`.out-of-scope/` のすべてのファイルを読みます。新しいイシューを評価するとき:

- リクエストが既存の out-of-scope 概念に一致するか確認します
- 一致はキーワードではなく概念の類似性で判断します — 「ナイトテーマ」は `dark-mode.md` に一致します
- 一致がある場合はメンテナに表面化します: 「これは `.out-of-scope/dark-mode.md` に類似しています — 以前これを拒否しました。[理由] のためです。今も同じ考えですか?」

メンテナは次のいずれかを行えます:

- **確認** — 新しいイシューは既存ファイルの "Prior requests" リストに追加され、クローズされます
- **再考** — out-of-scope ファイルが削除・更新され、イシューは通常のトリアージを進めます
- **不同意** — イシューは関連はあるが別物で、通常のトリアージを進めます

## `.out-of-scope/` に書き込むタイミング

**拡張機能** (バグではない) が `wontfix` として*拒否*された場合のみです。これはイシューとまったく同じように拡張機能の PR にも適用されます — 拒否された PR は、同じリクエストが新しいコードとして戻ってこないようにここに記録されます。

何かが**すでに実装されている**ために `wontfix` としてクローズされた場合は、ここに**書かないでください**。それは拒否された機能ではなく構築済みの機能です。記録すると誤った拒否で重複排除チェックを汚染します。代わりに、クローズコメントが機能が既に存在する場所を指し示します。

フロー:

1. メンテナが機能リクエストを対象外と判断する
2. 一致する `.out-of-scope/` ファイルが既に存在するか確認する
3. あれば: 新しいイシューを "Prior requests" リストに追記する
4. なければ: 概念名、決定、理由、最初の prior request を持つ新しいファイルを作成する
5. 決定を説明し `.out-of-scope/` ファイルに言及するコメントをイシューに投稿する
6. `wontfix` ラベルを付けてイシューをクローズする

## out-of-scope ファイルの更新・削除

メンテナが以前拒否した概念について考えを変えた場合:

- `.out-of-scope/` ファイルを削除します
- スキルは古いイシューを再オープンする必要はありません — それらは歴史的な記録です
- 再考のきっかけとなった新しいイシューは通常のトリアージを進めます
