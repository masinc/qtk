## Context

Backlog.md の最大の問題は「`task edit -d` 等でカスタム frontmatter が消失する」ことだった。CLI での更新時に、ユーザーが手動で追加したフィールドがエラーにならず静かに削除される。これは qtk の存在意義の一つを脅かす問題だった。

## Decision

YAML パースに **`Bun.YAML` (Bun 組込、依存ゼロ)** を主に使用し、全フィールド (既知・未知問わず) を保持する。

実装方針:
- **パース時に全フィールドを保持** — `Bun.YAML.parse` で frontmatter をオブジェクトとしてパース。既知・未知問わず全フィールドを保持
- **更新時にマージ** — スプレッド構文 (`{ ...record, ...updates }`) で既知フィールドを上書きしつつ未知フィールドを保持
- **シリアライズ時に全フィールドを出力** — `Bun.YAML.stringify` で保持した全フィールドを YAML に書き戻す
- **型定義は Partial** — TypeScript の型は既知フィールドを optional とし、インデックスシグネチャ `[key: string]: unknown` で未知フィールドを許容

フォールバックとして `yaml` (npm) を追加可能 (コメント保持や複雑な YAML 構造が必要な場合)。

却下した代替案:
- **`gray-matter`** — Markdown + frontmatter に特化しているが不要な機能が過多。frontmatter のみの用途には重い
- **自前パーサー** — 実装コストが高く、バグリスクがある

## Consequences

**ポジティブ**:
- Backlog.md の最大問題 (カスタム frontmatter 消失) を解決
- ユーザーが自由に frontmatter にフィールドを追加でき、CLI でも消失しない
- プロトタイプ検証済み: `parse → object → stringify` で未知フィールドが保持されることを確認

**ネガティブ**:
- `Bun.YAML` はコメント保持や複雑な YAML 構造に制限がある可能性 (R13)
- Bun ランタイム必須 (Node.js 単体では動作しない)

**リスク**:
- `Bun.YAML.stringify` の制限。緩和策として `yaml` (npm) へのフォールバックを設計に組み込んでおり、必要時に追加可能
