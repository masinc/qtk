## Context

既存のローカル課題管理ツールでは連番 ID の採番に問題があった:
- **Backlog.md** — ロックなしの連番方式。並列実行で採番順がずれる (実測済み)
- **現行 `.scratch` 規約** — 並列セッションで採番衝突が起きる

また、種別ごとに独立採番 (TSK-001 / ADR-001) する方式は将来種別が増えた時の拡張性が低い。

## Decision

**共通採番・プレフィックスなし・#NNNN 形式** (デフォルト4桁) を採用する。

- **共通採番**: 全種別 (issue / adr / spec / plan) で同一の通し番号を使用 (例: #0001 issue, #0002 adr, #0003 spec, #0004 plan)
- **プレフィックスなし**: `#0001` 形式。種別は frontmatter の `type` とディレクトリで判別
- **原子的採番**: ファイルロック (proper-lockfile の mkdir 方式) で採番の原子性を保証。並列セッションでの衝突を防ぐ
- **設定変更可能**: `config.yml` の `idDigits` で桁数を変更可能

却下した代替案:
- **連番 (ロックなし、Backlog.md 方式)** — 並列実行で採番順がずれる。ユーザーの元々の不満と同じ
- **ハッシュ ID (Beads 方式)** — 人間が読みにくい。`#a3f9c2` では何番目か分からない
- **ハイブリッド (連番 + 短ハッシュ)** — 複雑で実装コストが高い。ファイルロック付き連番で十分
- **種別ごと独立採番 (TSK-001 / ADR-001)** — 将来種別が増えた時の拡張性が低い
- **プレフィックス付き (#ISSUE-0001 等)** — 冗長

## Consequences

**ポジティブ**:
- 並列セッションで ID 衝突が起きない (ファイルロックで保証)
- 全レコードが一意の ID を持ち、種別をまたいで参照可能
- `#0001` 形式で人間が読みやすい

**ネガティブ**:
- 種別ごとに ID が飛び飛びになる (issue が #0001, #0005, #0008 のように)。ただし ID は一意特定が目的なので問題ない
- ファイルロックのオーバーヘッド (採番時にロック取得が必要)

**リスク**:
- ネットワークファイルシステムでのロック挙動。緩和策として proper-lockfile の mkdir 方式 (ネットワーク FS でも原子性保証) を採用。フォールバックとして自前 mkdir ロックも実装済み
